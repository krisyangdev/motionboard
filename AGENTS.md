# Site template: notes for agents

The template every site is built from: React 19 + TanStack Start/Router/Query + Tailwind CSS v4 + coss ui (Base UI), prerendered and served by one Cloudflare Worker. Demo: https://template.krisyang.dev. Status and log: `~/code/home/projects/site-template.md`. Shared site rules: `~/code/home/lines/sites.md`. Look and tokens: `DESIGN.md`.

## Commands
- `npm run dev`: dev server on http://127.0.0.1:3000.
- `npm run build`: writes the generated public files (robots, `_redirects`, `_headers`, llms.txt, video sitemap), then builds and prerenders every page in every language into `.cloudflare/output/v1/workers/default/assets`.
- `npm test`: unit tests (Vitest), build, then `scripts/test.mjs` checks the output: sitemap = exactly the indexable pages, hreflang (per page: its indexable languages plus x-default), canonical (self), titles (length, unique), descriptions (length, unique per language), exactly one h1 that contains the keyword, hub pagination pages (self-canonical, not in the sitemap, linked), the about page's Organization node (`/about/#org`), `<html lang dir>`, JSON-LD (valid, types per page type, no FAQPage, visible breadcrumb = JSON-LD breadcrumb = registry), og:image, year in title = `updated` year, internal links, redirects, robots, headers, llms.txt, noindex outside the sitemap, and that no page starts its JS before LCP or links an external stylesheet.
- `npm run seo-report`: per page type and language, how many pages are indexable and which are noindex, with the reasons from the quality gates (reads content only, no build).
- `npm run typecheck`: `tsc --noEmit` (run after a build or dev start, which generates `src/routeTree.gen.ts`).
- `npm run deploy`: build, `cf deploy` (never wrangler), IndexNow ping.
- `npm run e2e`: the money path end to end in Chromium (Playwright) against the built Worker on http://127.0.0.1:3000 with the mocks on: sign up → verification email → signup credits → buy a pack through the mock Dodo checkout (real signed webhook into the real handler) → replayed webhook grants nothing → generate (hold → commit) → a failing generation is refunded → admin bootstrap, sign-in, credit adjust, audit row. Passing = `1 passed`. Stop `npm run dev` first (same port). Against the live demo: `E2E_BASE_URL=https://template.krisyang.dev E2E_BOOTSTRAP_TOKEN=$(security find-generic-password -s site-template-admin-bootstrap -a template -w) npm run e2e`. Playwright prints request headers when a step fails, so rotate the bootstrap token after a failed live run.
- `npm run db:generate` after editing `src/core/db/schema.ts` (writes `migrations/NNNN_*.sql`); `npm run db:migrate:local` / `db:migrate:remote` apply them (`cf d1 migrations apply`).
- `npm run lighthouse -- --url <url> [--perf 99]`: local Lighthouse gate (95 per category by default). Its performance numbers run behind the local proxy and come out lower; pagespeed.web.dev mobile is the reference for the 99 gate (the anonymous PSI API quota is often used up, so use the web page).

## Who owns what
Sites merge template updates, so the split matters:
- Template-owned (sites do not edit; fix it in the template and merge): `src/core/**`, `scripts/**`, `src/router.tsx`, `vite.config.ts`, `vitest.config.ts`, `tsconfig.json`, `components.json`, `DESIGN.md`, this file's template sections.
- Site-owned (each site edits freely): `site.config.ts`, `cloudflare.config.ts`, `src/site/**`, `content/**`, `public/**` (except the generated files), the route files a site adds, `README.md`, the "Site notes" section at the end of this file.
- Shared route files under `src/routes/` (root, locale layout, tools, guides, hubs, about, legal) ship with the template; a site may change them, accepting a merge conflict when the template changes them too.

## Where things are
- `site.config.ts`: domain, name, languages, home title/description, OG image, contact email, PostHog key variable, IndexNow key, llms.txt switch, CSP allowlist. The only place for these values; scripts import it too.
- i18n: the language list is `languages` (+ `defaultLang`) in `site.config.ts`; everything that depends on a language reads it, so adding a language changes no code. `src/core/locale-data.ts` (registry: hreflang, og, intl, dir, name per URL code), `src/core/i18n.ts` (pure rules: default language at the root, others under `/<lang>/`; paths passed around are default-language paths with leading and trailing slash; `HTML_LANG`, `OG_LOCALE`, `DIR`, `INTL_LOCALE`, `formatDate`, `formatNumber`; it checks the config on import and throws an error saying what to fix), `src/core/locale.tsx` (`useLocale()`, `useLocaleParam()`, `useMessages()`, `useCoreMessages()`). Routes live under `src/routes/{-$locale}/`; `route.tsx` there 404s unknown prefixes and the default language's prefix. UI strings: `src/core/messages/<code>.ts` (one file per language: shell, page templates, account/app pages, emails; `en.ts` defines the type), `src/site/messages.ts` (site, `Record<Locale, …>`). Admin is English only. Links in the current language: `<Link to="/{-$locale}/tools/$slug/" params={{ locale: useLocaleParam(), slug }}>`.
- No fallback for content: a page exists in a language only when that language has content for it (`pageLocales(page)` in `src/core/pages.ts`: the languages with a title). A missing translation means no page in that language (404, no sitemap entry, no hreflang), never another language's text under `/<code>/`. Home exists in every language (`SITE.title` and `description` need every language). The tools and guides hubs exist in a language only when they have a text block there and at least one member. The language switcher links to the same page where it exists, else to that language's home.
- SEO: `seoHead()` and JSON-LD helpers in `src/core/seo.ts`; every route's `head()` uses it. `seoHead({ breadcrumb })` writes the BreadcrumbList from the same `Crumb[]` the page shows (`trail()` and `<Breadcrumb crumbs>` in `src/core/pages/HubPage.tsx`). Every page's graph points at the Organization by `@id` (`ORG_ID`, `/about/#org`). There is no FAQPage JSON-LD: the FAQ is visible content only. The page list for the sitemap, llms.txt and redirects is `sitePages()` in `src/core/pages.ts` (each page has `type`, `keyword`, `indexable`/`reasons`, `lastmod`, `breadcrumb`); extra static pages go in `src/site/pages.ts` (`ExtraPage`). Sitemap with hreflang alternates (the languages the page exists in, plus x-default) is written by TanStack's prerender (`vite.config.ts`).
- Content contract: `src/core/content/schema.ts` (zod). Every tool JSON and MDX frontmatter is validated when `sitePages()` / `contentIndex()` read it; a bad file stops the build with its path and field. Each indexable page has per language `keyword` (unique per language across the site, contained in the title), `demand` (`{source, note, checked}`: where the demand for the keyword was checked; `none` is not allowed on tools and guides), `title` (60 characters, 32 CJK, without the site name), `description` (120-160, 50-90 CJK), `lede`, optional `h1` (default: the keyword); plus `published` and `updated` (YYYY-MM-DD). Guides add `kind`. In MDX frontmatter, nested values (`demand`, `sources`, `faq`) are one-line JSON.
- Page types and templates (each route is a thin file over a template in `src/core/pages/`, built from the blocks in `src/core/ui/page/`: Breadcrumb, Byline, FaqList, RelatedGrid, StepsList, SourcesList, Pagination, Evidence, Examples):
  - Tool: `content/tools/<slug>.json` (`ToolPage.tsx`; a tool needs a widget id from `src/site/tools/index.ts`, a page without a tool is a guide); fields beyond the common ones: `steps` (3-4), `examples`, `limits`, `sections` (1-3), `faq`, `related`.
  - Guide, about, legal: MDX in `content/guides/<lang>/`, `content/about/<lang>/about.mdx`, `content/legal/<lang>/` (`DocPage.tsx`). MDX can use `<Evidence caption="…">` for first-hand tables and images. Guides take `sources` and `related` (slugs, guides then tools) in the frontmatter; guide and about take `faq`.
  - Hub: `content/hubs/<tools|guides>.json` (`HubPage.tsx`): `keyword`, `demand` (`none` allowed), `intro`, optional `sections`/`faq`, optional `pageSize` (default and maximum 60). Members are the collection's indexable pages. Further pages are `/<hub>/page/<n>/` (route files `page/$n.tsx`): prerendered, self-canonical, a numbered title and h1, never in the sitemap, linked with plain `<a href>`. A hub exists in a language only when it has a text block there and at least one member. Without a hub file there is no hub page and the Tools/Guides breadcrumb level is left out.
  - Slots: `src/site/slots.tsx` (`PageSlots` in `src/core/ui/page/slots.ts`: `afterLede`, `afterContent`, `card`) lets a site add visuals to these templates without forking a route.
- Quality gates: `src/core/seo/quality.ts` decides per page and language whether it may be indexed (minimum content per type: tool 250 words / 450 CJK characters, 3-4 steps, 4 FAQ items, 1 example; guide 600 / 1100, 2 H2, 3 in-copy internal links, 1 first-hand element; hub 6 indexable members and a 50-word intro, lowered with `seo.hubMinMembers` in `site.config.ts`; about 150 / 280; legal 100 / 180 or `noindex: true`). A page below its minimum is still built and linkable, but noindex (`noindex,follow`, no canonical or hreflang), out of the sitemap, llms.txt, hub lists and the hreflang sets of its other languages. `SitePage.noindex` (language → reasons), `SitePage.indexable` and `indexableLocales(page)` carry the result; the app reads it from `index.pages` of `virtual:content-index` (`seoState()`, `isIndexable()` in `src/core/content/exists.ts`). Run `npm run seo-report` to see the reasons. Lists read `virtual:content-index` (names, frontmatter, the languages of each page and which are noindex; built by `contentIndex()` in `src/core/pages.ts`), so a page chunk never bundles other pages' text. Restart `npm run dev` after adding a content file.
- Generated public files: `scripts/generate.mjs` (run by the build): `robots.txt`, `_redirects` (from `content/renamed.json`, every language, with and without trailing slash), `_headers` (security headers + CSP from `src/core/headers.ts`, immutable caching for `/assets/*` and `/fonts/*`), `llms.txt`, `sitemap-video.xml` (from `content/videos.json`). They are gitignored.
- Analytics: `src/core/track.ts` (PostHog capture API, cookieless, no SDK; no key = console + `window.__events`), `src/core/Analytics.tsx` (page_view, errors → `$exception`, `data-cta` link clicks), page types in `src/site/analytics.ts`. Every event carries `site` and `lang`. Cloudflare Web Analytics is turned on per zone in the dashboard, not in code.
- Shell: `src/core/shell/` (Header, Footer, ThemeToggle, LanguageSwitch, NotFound), nav links in `src/site/nav.ts`. Theme: `.dark` class set before paint by `THEME_SCRIPT` (`src/core/theme.ts`).
- coss ui: `src/core/ui/` (shadcn CLI, `components.json`, registry `@coss`). Only components in use are kept: every class in `src/` ends up in the CSS inlined in every page. Add with `npx shadcn@latest add @coss/<name>`.

## Performance rules (PSI mobile 99+)
- The Cloudflare account is on Workers Free (10 ms CPU per request, 100k requests/day shared by every site): public pages are prerendered static assets (no Worker CPU); keep per-request work small in API routes (password hashing ~12k PBKDF2 iterations at most, no heavy SSR).
- Every public page is prerendered; all CSS is inlined in `<head>` (`?inline` import in `__root.tsx`); one self-hosted font (Inter Latin, preloaded) with a metric-matched Arial fallback, so the swap causes no layout shift.
- `src/core/Scripts.tsx` replaces TanStack's `<HeadContent>`/`<Scripts>`: the app JS (entry + modulepreloads) is only added once every element with an `elementtiming` attribute in the first viewport has painted (3 s fallback). Mark the LCP element with `elementtiming="lcp"` (images also `fetchPriority="high"`). Otherwise Lighthouse counts the JS toward LCP and mobile scores drop to 90–95 (seen on Motionboard).
- Popup components (menu, select, dialog, sheet, toast, tooltip, popover) never render in the first screen of a content page and are never imported by the shell; FAQs are native `<details>`; widgets load after hydration inside a fixed-height slot.
- Measured 2026-11-26 on template.krisyang.dev, PSI mobile: home 100/100/100/100, tool page 100/100/100/100.

## Accounts, credits, payments (layer 1)
Everything runs in the same Worker as the pages: `src/server.ts` is the entry (`fetch` → TanStack Start, `queue` → job consumer, `scheduled` → cron every 10 min). Turn accounts off with `SITE.accounts.enabled = false` (the header link and account APIs go away).

- Env: `src/core/server/env.ts` (`AppEnv`, `appEnv()`, `flag()`); bindings in `cloudflare.config.ts`. Local values in `.dev.vars` (copy `.dev.vars.example`). Only bindings declared `bindings.secret()` take local values from `.dev.vars` (text bindings cannot be overridden locally), which is why `BETTER_AUTH_URL` is a secret. Production secrets: `cf workers secrets update <NAME> --worker <worker> --type secret_text --text …` for `BETTER_AUTH_URL` (`https://<domain>`), `BETTER_AUTH_SECRET`, `ADMIN_BOOTSTRAP_TOKEN`, and when used `DODO_PAYMENTS_API_KEY`, `DODO_PAYMENTS_WEBHOOK_SECRET`, `RESEND_API_KEY`, `TURNSTILE_SECRET_KEY`, `POSTHOG_KEY`, `GOOGLE_CLIENT_ID/SECRET`. The template demo's values live in the macOS keychain (`site-template-*`). Never print or commit them.
- Mocks (`MOCK_PAYMENTS`, `MOCK_EMAIL`, `MOCK_GENERATION` = `true`): a mock Dodo checkout page (`/api/mock/dodo/checkout`) whose Pay button signs a Dodo-format webhook with the webhook secret and hands it to the real webhook handler; emails stored in R2 under `mock-emails/` and readable at `GET /api/mock/emails` with the `x-bootstrap-token` header; generation by `src/core/jobs/mock-provider.ts` (a prompt containing "fail" fails). The template demo runs fully on mocks.
- DB: `src/core/db/schema.ts` (Drizzle, D1). Better Auth tables + `credit_accounts`, `credit_transactions` (append-only, unique `(type, source_type, source_id)` so nothing applies twice), `credit_reservations`, `payment_orders`, `payment_webhook_events`, `jobs`, `rate_limits`, `admin_users`, `admin_sessions`, `admin_audit_logs`.
- Auth: `src/core/auth/server.ts` (Better Auth: email + password with required verification, Google when its keys are set, Dodo plugin, signup credits in the user-create hook), `session.ts` (`getSessionUser`, `requireUser`), `client.ts`. Pages: `src/routes/{-$locale}/{login,signup,forgot-password,reset-password,account,app}.tsx` (noindex, rendered per request, never prerendered: `PRIVATE_PATHS` in `src/core/pages.ts`).
- Credits: only `src/core/credits/ledger.ts` changes balances (`grant`, `hold`, `commit`, `refund`, `adjust`; each one D1 batch guarded so a failed check changes nothing). Tests: `ledger.test.ts` on in-memory SQLite.
- Payments: `src/core/billing/` (`checkout.ts` creates an order then a Dodo checkout session; `webhooks.ts` verifies amount/currency/product, records the event once, grants credits once, marks the order paid; refunds and failures update the order). Packs: `src/site/plans.ts`. Portal: `POST /api/billing/portal`.
- Jobs: `POST /api/jobs` → `src/core/jobs/create.ts` (Turnstile, rate limit, hold credits, queue message) → `queue.ts` (runs the provider from `src/site/generation.ts`, stores the file in R2, commits; retries 3×, then fails and refunds) → `cron.ts` settles stale reservations. Files: `GET /api/files/<key>` (owner only).
- Abuse: `src/core/security/rate-limit.ts` (D1 fixed window, one atomic upsert), `turnstile.ts` (skipped when no secret key is set).
- Email: `src/core/email/send.ts` (Resend HTTP API), `templates.ts` (verify, reset, receipt; per locale).
- Server analytics and errors: `src/core/server/track.ts` (`trackServer`, `captureServerException` → PostHog `$exception`).
- Admin: separate identity (not Better Auth). `src/core/admin/` + `src/routes/api/admin/*` + `src/routes/admin/*` (English, no site chrome). First admin: `curl -X POST https://<domain>/api/admin/bootstrap -H "x-bootstrap-token: …" -H 'content-type: application/json' -d '{"email":"…","password":"…"}'` (also resets that admin's password and sessions). Every credit adjust and login is in the audit log.

### Recipes
- Add a credit pack: add an entry to `src/site/plans.ts` (code, credits, price in minor units, currency, Dodo product ids per mode). Create the product in the Dodo dashboard (test mode first) and paste its id. `npm run e2e` buys `plans[0]`.
- Add a paid action (a generation kind): add a provider to `src/site/generation.ts` (`cost`, `run`); the client posts `{ kind, input }` to `/api/jobs`. Nothing else changes: holding, retries, refunds and storage are core.
- Add a queue job of another kind: same path; a provider's `run` can do any work that returns a file. Work that returns no file belongs in a new core handler; ask before adding one.
- Add an admin view: a list query in `src/core/admin/queries.ts`, a route in `src/routes/api/admin/` (`requireAdmin` first, `audit()` for any write), a page in `src/routes/admin/` using `src/core/admin/ui.tsx`, and a link in `src/routes/admin/route.tsx`.
- Change the schema: edit `src/core/db/schema.ts`, `npm run db:generate`, `npm run db:migrate:local`, test, then `npm run db:migrate:remote` before deploying.
- Use an existing password hash format (users moved in from an older auth): set `password` in `src/site/auth.ts` to `{ hash, verify }`; core passes it to Better Auth as `emailAndPassword.password`. Test: `src/core/auth/password.test.ts` (ShotFrames' `i2s-pbkdf2:<salt>:pbkdf2-sha256:<n>:<hash>` format through a real sign-in).
- Receive the payment webhook at another path (e.g. a URL already registered in Dodo live mode): add a site route file, e.g. `src/routes/payments/webhooks/dodo.ts`, whose `POST` returns `auth().handler(new Request(new URL('/api/auth/dodopayments/webhooks', request.url), request))`. Signature checks and idempotency are unchanged.
- Move existing credit data in: map each user's balance to one `credit_accounts` row (`available`, `frozen`); history rows to `credit_transactions` with `type` grant|purchase|hold|commit|refund|adjust, `source_type`/`source_id` (dedupe on the unique `(type, source_type, source_id)` first), and `available_after`/`frozen_after`; open holds to `credit_reservations` with status `held` (others `committed`/`refunded`). The balance is the `credit_accounts` row, kept by `ledger.ts`; the DB has no triggers, so drop any balance triggers from the old database.
- Go live with real payments: in Dodo create the live products and a webhook to `https://<domain>/api/auth/dodopayments/webhooks`; set `DODO_PAYMENTS_ENVIRONMENT=live_mode`, `MOCK_PAYMENTS=false` and the two Dodo secrets. Real payments need Rui's OK.

## Add a language
No code changes.
1. `site.config.ts`: add the code to `languages` and its text to `title` and `description`.
2. If the code is not in `src/core/locale-data.ts`, or `src/core/messages/<code>.ts` does not exist, add them in the template (copy `en.ts`, translate) and merge into the sites.
3. Fill the new entries in `src/site/messages.ts`, `src/site/nav.ts` and the other `Record<Locale, …>` data of the site (`npm run typecheck` lists them).
4. Add content: `content/guides/<code>/…`, `content/legal/<code>/…`, `content/about/<code>/about.mdx`, a `<code>` block in each `content/tools/*.json` and `content/hubs/*.json`. Pages without a translation do not exist in that language.
5. `npm test`.

## Starting a new site from the template
1. `gh repo create krisyangdev/<slug> --private` and clone the template into `~/code/sites/<slug>` (`git clone git@github.com:krisyangdev/site-template.git <slug>`), then `git remote rename origin template` and `git remote add origin <new repo>`; `git push -u origin main`.
2. Edit `site.config.ts` (id, name, domain, worker, languages, copy, email, IndexNow key + `public/<key>.txt`), `src/site/styles.css` (`--brand` light/dark), `public/favicon.svg`, `public/og.png`, `cloudflare.config.ts` (bindings).
3. Replace the demo content in `content/`, `src/site/home/`, `src/site/tools/`, `src/site/nav.ts`.
4. `npm test`, `npm run deploy`, check the live URL and PSI.

## Taking template updates into a site
`git fetch template && git merge template/main`, resolve conflicts (site-owned files keep the site's version), `npm install`, `npm test`, deploy. Make shared fixes in the template first, then merge them into each site; never fix `src/core/` only in a site.

## Adopting the template in an existing site (e.g. Motionboard)
Add the template as a remote and merge with unrelated histories (`git remote add template …; git fetch template; git merge template/main --allow-unrelated-histories`), or start from a fresh clone and copy the site's content in. Then move: site config values into `site.config.ts`; the duplicated `/zh/` route tree into `{-$locale}` routes; `seo.ts`/`track.ts`/`Scripts.tsx`/scripts to the core versions; hand-written CSS to Tailwind + coss tokens; keep site-only parts (data generators, video components, D1 bindings) under `src/site/` and `scripts/site/`. Acceptance: same URLs (sitemap diff empty), `npm test` green, PSI mobile ≥ 99 on home and one deep page.

## Decisions (2026-11-26, template dev)
- npm, single package (no monorepo), Node 22 (type stripping for `site.config.ts` in scripts).
- i18n with the official `{-$locale}` optional segment and plain typed dictionaries per locale (no Paraglide compile step): our sites carry few UI strings; page text lives in content files that are loaded per page.
- MDX through `@mdx-js/rollup` + `import.meta.glob` (no Content Collections): fewer moving parts, one chunk per document.
- Fonts: Inter only (coss default), Latin subset self-hosted; Geist Mono dropped for the system mono.
- coss `html { font-sans font-mono }` from the registry was a bug (everything rendered mono); fixed to `font-sans` in `app.css`.
- Template demo runs on `template.krisyang.dev` (a throwaway subdomain of an existing zone).
