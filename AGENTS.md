# Site template: notes for agents

The template every site is built from: React 19 + TanStack Start/Router/Query + Tailwind CSS v4 + coss ui (Base UI), prerendered and served by one Cloudflare Worker. Demo: https://template.krisyang.dev. Status and log: `~/code/home/projects/site-template.md`. Shared site rules: `~/code/home/lines/sites.md`. Look and tokens: `DESIGN.md`.

## Commands
- `npm run dev`: dev server on http://127.0.0.1:3000.
- `npm run build`: writes the generated public files (robots, `_redirects`, `_headers`, llms.txt, the sitemaps, feed.xml), then builds and prerenders every page in every language into `.cloudflare/output/v1/workers/default/assets`.
- `npm test`: unit tests (Vitest), build, then `scripts/test.mjs` checks the output: sitemap index and child sitemaps (well formed, `lastmod`, no priority/changefreq, each page in the child of its type), their union = exactly the indexable pages, feed.xml and changelog/rss.xml, content hashes (`npm run stamp`), hreflang (per page: its indexable languages plus x-default), canonical (self), titles (length, unique), descriptions (length, unique per language), exactly one h1 that contains the keyword, hub pagination pages (self-canonical, not in the sitemap, linked), item pages (ImageObject/VideoObject, media with alt and size, 4-level breadcrumb, noindex items out of sitemap, llms.txt and hub lists), the compare/alternatives/glossary/use-case/gallery/changelog pages (visible "Updated" date = JSON-LD date, disclosure line, table of 6 rows, gallery images with alt, size and lazy loading, changelog sections and feed), the about page's Organization node (`/about/#org`), `<html lang dir>`, JSON-LD (valid, types per page type, no FAQPage, visible breadcrumb = JSON-LD breadcrumb = registry), og:image, year in title = `updated` year, internal links, redirects, robots, headers, llms.txt, noindex outside the sitemap, and that no page starts its JS before LCP or links an external stylesheet.
- `npm run seo-report`: per page type (per collection for items) and language, how many pages are indexable and which are noindex, with the reasons from the quality gates, and the stale pages (comparison and alternatives older than 180 days, guides older than 365; a warning only). Reads content only, no build. Exits 1 when a collection is above `seo.maxNoindexShare`.
- `npm run typecheck`: `tsc --noEmit` (run after a build or dev start, which generates `src/routeTree.gen.ts`).
- `npm run stamp`: sets `updated` to today in every content file whose content changed and records the hashes in `content/.hashes.json` (commit it). `npm run stamp -- --minor <slug>` records a change and keeps the date (typo fixes). See "Freshness, sitemaps, feed".
- `npm run deploy`: build, `cf deploy` (never wrangler), crawler check (`npm run check-crawlers`), IndexNow ping (`npm run indexnow`; `-- --all` pings every URL).
- `npm run e2e`: the money path end to end in Chromium (Playwright) against the built Worker on http://127.0.0.1:3000 with the mocks on: sign up → verification email → signup credits → buy a pack through the mock Dodo checkout (real signed webhook into the real handler) → replayed webhook grants nothing → generate (hold → commit) → a failing generation is refunded → admin bootstrap, sign-in, credit adjust, audit row. Passing = `1 passed`. Stop `npm run dev` first (same port). Against the live demo: `E2E_BASE_URL=https://template.krisyang.dev E2E_BOOTSTRAP_TOKEN=$(security find-generic-password -s site-template-admin-bootstrap -a template -w) npm run e2e`. Playwright prints request headers when a step fails, so rotate the bootstrap token after a failed live run.
- `npm run db:generate` after editing `src/core/db/schema.ts` (writes `migrations/NNNN_*.sql`); `npm run db:migrate:local` / `db:migrate:remote` apply them (`cf d1 migrations apply`).
- `npm run lighthouse -- --url <url> [--perf 99]`: local Lighthouse gate (95 per category by default). Its performance numbers run behind the local proxy and come out lower; pagespeed.web.dev mobile is the reference for the 99 gate (the anonymous PSI API quota is often used up, so use the web page).

## Who owns what
Sites merge template updates, so the split matters:
- Template-owned (sites do not edit; fix it in the template and merge): `src/core/**`, `scripts/**`, `src/router.tsx`, `vite.config.ts`, `vitest.config.ts`, `tsconfig.json`, `components.json`, `DESIGN.md`, this file's template sections.
- Site-owned (each site edits freely): `site.config.ts`, `cloudflare.config.ts`, `src/site/**`, `content/**`, `public/**` (except the generated files), the route files a site adds, `README.md`, the "Site notes" section at the end of this file.
- Shared route files under `src/routes/` (root, locale layout, tools, guides, hubs, about, legal) ship with the template; a site may change them, accepting a merge conflict when the template changes them too.

## Where things are
- `site.config.ts`: domain, name, languages, home title/description, OG image, contact email, PostHog key variable, IndexNow key, llms.txt switch, CSP allowlist. The only place for these values; scripts import it too.
- i18n: the language list is `languages` (+ `defaultLang`) in `site.config.ts`; everything that depends on a language reads it, so adding a language changes no code. `src/core/locale-data.ts` (registry: hreflang, og, intl, dir, name per URL code), `src/core/i18n.ts` (pure rules: default language at the root, others under `/<lang>/`; paths passed around are default-language paths with leading and trailing slash; `HTML_LANG`, `OG_LOCALE`, `DIR`, `INTL_LOCALE`, `formatDate`, `formatNumber`; it checks the config on import and throws an error saying what to fix), `src/core/locale.tsx` (`useLocale()`, `useLocaleParam()`, `useMessages()`, `useCoreMessages()`). Routes live under `src/routes/{-$locale}/`; `route.tsx` there 404s unknown prefixes and the default language's prefix. UI strings: `src/core/messages/<code>.ts` (one file per language: shell, page templates, account/app pages, emails; `en.ts` defines the type), `src/site/messages.ts` (site, `Record<Locale, …>`). Admin is English only. Links in the current language: `<Link to="/{-$locale}/tools/$slug/" params={{ locale: useLocaleParam(), slug }}>`.
- No fallback for content: a page exists in a language only when that language has content for it (`pageLocales(page)` in `src/core/pages.ts`: the languages with a title). A missing translation means no page in that language (404, no sitemap entry, no hreflang), never another language's text under `/<code>/`. Home exists in every language (`SITE.title` and `description` need every language). The tools and guides hubs exist in a language only when they have a text block there and at least one member. The language switcher links to the same page where it exists, else to that language's home.
- SEO: `seoHead()` and JSON-LD helpers in `src/core/seo.ts`; every route's `head()` uses it. `seoHead({ breadcrumb })` writes the BreadcrumbList from the same `Crumb[]` the page shows (`trail()` and `<Breadcrumb crumbs>` in `src/core/pages/HubPage.tsx`). Every page's graph points at the Organization by `@id` (`ORG_ID`, `/about/#org`). There is no FAQPage JSON-LD: the FAQ is visible content only. The page list for the sitemap, llms.txt and redirects is `sitePages()` in `src/core/pages.ts` (each page has `type`, `keyword`, `indexable`/`reasons`, `lastmod`, `breadcrumb`); extra static pages go in `src/site/pages.ts` (`ExtraPage`). The sitemaps are written from the same list by `scripts/generate.mjs` (see "Freshness, sitemaps, feed"); the TanStack sitemap plugin is off.
- Content contract: `src/core/content/schema.ts` (zod). Every tool JSON and MDX frontmatter is validated when `sitePages()` / `contentIndex()` read it; a bad file stops the build with its path and field. Each indexable page has per language `keyword` (unique per language across the site, contained in the title), `demand` (`{source, note, checked}`: where the demand for the keyword was checked; `none` is not allowed on tools and guides), `title` (60 characters, 32 CJK, without the site name), `description` (120-160, 50-90 CJK), `lede`, optional `h1` (default: the keyword); plus `published` and `updated` (YYYY-MM-DD). Guides add `kind`. In MDX frontmatter, nested values (`demand`, `sources`, `faq`, `products`, `table`, `seeAlso`) are one-line JSON.
- Page types and templates (each route is a thin file over a template in `src/core/pages/`, built from the blocks in `src/core/ui/page/`: Breadcrumb, Byline, FaqList, RelatedGrid, StepsList, SourcesList, Pagination, Evidence, Examples):
  - Tool: `content/tools/<slug>.json` (`ToolPage.tsx`; a tool needs a widget id from `src/site/tools/index.ts`, a page without a tool is a guide); fields beyond the common ones: `steps` (3-4), `examples`, `limits`, `sections` (1-3), `faq`, `related`.
  - Guide, about, legal: MDX in `content/guides/<lang>/`, `content/about/<lang>/about.mdx`, `content/legal/<lang>/` (`DocPage.tsx`). MDX can use `<Evidence caption="…">` for first-hand tables and images. Guides take `sources` and `related` (slugs, guides then tools) in the frontmatter; guide and about take `faq`.
  - Hub: `content/hubs/<id>.json` (`HubPage.tsx`; id = `tools`, `guides` or a collection id) and `content/hubs/<collection>/<category>.json` for a category hub: `keyword`, `demand` (`none` allowed), `intro`, optional `name` (breadcrumb name of a collection or category hub), `sections`/`faq`, `pageSize` (default and maximum 60). Members are the hub's indexable pages. A collection hub links its category hubs. Further pages are `/<hub>/page/<n>/` (route files `page/$n.tsx`): prerendered, self-canonical, a numbered title and h1, never in the sitemap, linked with plain `<a href>`. A hub exists in a language only when it has a text block there and at least one member. Without a hub file there is no hub page and the Tools/Guides breadcrumb level is left out.
  - Item (programmatic page): a collection declared in `src/site/collections.ts`, one file per item in `content/collections/<id>/<slug>.json`, at `/<id>/<slug>/` (`ItemPage.tsx`, loader `loadCollectionPage`). Fields: `category` (category ids), `tags`, optional `related` (slugs), optional `media` (image or video), `data` (the collection's zod schema), and per language `name`, optional `ownName`, `keyword`, `demand`, `title`, `description`, `lede`, `body` (blocks `{h2, body}`), `alt` (required with media), `faq` (0-4). The language block exists only when it has `name`, `keyword` and `body`. Order: breadcrumb (Home, collection, category, name), h1 = `name`, lede, media, the site's `itemData` slot, body, FAQ, related items (3 to 8: the item's `related`, else same category, then shared tags, chosen at build time). JSON-LD: BreadcrumbList and ImageObject or VideoObject (`uploadDate` = `published`) for the main media; no FAQPage.
  - Compare (`content/compare/<lang>/<a>-vs-<b>.mdx`, `/compare/<a>-vs-<b>/`, `ComparePage.tsx`), glossary term (`content/glossary/<lang>/<slug>.mdx`, `/glossary/<slug>/`, `GlossaryPage.tsx`): MDX with one-line JSON frontmatter values. Alternatives (`content/alternatives/<product>.json`, `/alternatives/<product>/`), use case (`content/use-cases/<slug>.json`, `/for/<slug>/`), gallery (`content/gallery/<slug>.json`, `/gallery/<slug>/`): JSON with a text block per language like a tool. Changelog: `content/changelog/changelog.json`, `/changelog/` (entries `{date, slug, title, items}`, newest first, 50 per page, `/changelog/page/<n>/`, RSS at `/changelog/rss.xml`). Fields and minimums: "Adding a page". A compare hub (`content/hubs/compare.json`, `/compare/`) and a glossary index (`content/hubs/glossary.json`, `/glossary/`) use the hub machinery and exist only when the site adds those hub files.
  - Slots: `src/site/slots.tsx` (`PageSlots` in `src/core/ui/page/slots.ts`: `afterLede`, `afterContent`, `card`, `itemData`) lets a site add visuals to these templates without forking a route.
- Quality gates: `src/core/seo/quality.ts` decides per page and language whether it may be indexed (minimum content per type: tool 250 words / 450 CJK characters, 3-4 steps, 4 FAQ items, 1 example; guide 600 / 1100, 2 H2, 3 in-copy internal links, 1 first-hand element; hub 6 indexable members and a 50-word intro, lowered with `seo.hubMinMembers` in `site.config.ts`; about 150 / 280; legal 100 / 180 or `noindex: true`; item 80 words / 150 CJK characters of its own text (lede, body, FAQ, `dataText`), an image or video or a data block of 10 entries, 3 related items, no near-duplicate in its collection and language: 5-word shingles, 4-character for CJK, Jaccard above 0.6 fails, and the later item of a pair is the one that fails; compare, alternatives, glossary, use case, gallery and changelog: see "Adding a page"; their near-duplicate check runs within the type and language, at 0.4 for use cases). An item below its minimum is not a build error; the build fails only when more than `seo.maxNoindexShare` (default 0.2 in `site.config.ts`) of a collection's items in one language are noindex, with a message naming the collection and the noindex items. A page below its minimum is still built and linkable, but noindex (`noindex,follow`, no canonical or hreflang), out of the sitemap, llms.txt, hub lists and the hreflang sets of its other languages. `SitePage.noindex` (language → reasons), `SitePage.indexable` and `indexableLocales(page)` carry the result; the app reads it from `index.pages` of `virtual:content-index` (`seoState()`, `isIndexable()` in `src/core/content/exists.ts`). Run `npm run seo-report` to see the reasons. Lists read `virtual:content-index` (names, frontmatter, the languages of each page and which are noindex; built by `contentIndex()` in `src/core/pages.ts`), so a page chunk never bundles other pages' text. Restart `npm run dev` after adding a content file.
- Content folders: `content/{tools,guides,legal,about,hubs,collections,compare,alternatives,glossary,use-cases,gallery,changelog}`; `content/renamed.json`, `content/videos.json`, `content/.hashes.json`. Page blocks added for these types: `CompareTable` (`src/core/ui/page/`), templates `ComparePage`, `AlternativesPage`, `GlossaryPage`, `UseCasePage`, `GalleryPage`, `ChangelogPage` (`src/core/pages/`), JSON loaders `src/core/content/pagefiles.ts`, `definedTermLd` in `src/core/seo.ts`, stale pages in `src/core/seo/freshness.ts`. Demo images for the gallery: `public/gallery/`.
- Generated public files: `scripts/generate.mjs` (run by the build): `robots.txt`, `_redirects` (from `content/renamed.json`, every language, with and without trailing slash), `_headers` (security headers + CSP from `src/core/headers.ts`, immutable caching for `/assets/*` and `/fonts/*`), `llms.txt`, `sitemap.xml` (index) with its child sitemaps, `sitemap-video.xml` (from `content/videos.json` and the video items), `feed.xml`, `changelog/rss.xml`. Every `public/sitemap*.xml` is generated. They are gitignored.
- Analytics: `src/core/track.ts` (PostHog capture API, cookieless, no SDK; no key = console + `window.__events`), `src/core/Analytics.tsx` ($pageview, errors → `$exception`, `data-cta` link clicks), page types in `src/site/analytics.ts`. Every event carries `site` and `lang`. Events use PostHog's cookieless mode (`distinct_id: $posthog_cookieless`, PostHog hashes the id server-side per day, nothing stored in the browser), the landing URL's UTM/click-id/`ref` params, and the country from `/cdn-cgi/trace` (the first flush waits up to 1.5 s for it); bot user agents send nothing. Cloudflare Web Analytics is turned on per zone in the dashboard, not in code.
- Shell: `src/core/shell/` (Header, Footer, ThemeToggle, LanguageSwitch, NotFound), nav links in `src/site/nav.ts`. Theme: `.dark` class set before paint by `THEME_SCRIPT` (`src/core/theme.ts`); `SITE.theme.default` 'system' follows the system preference, 'light' stays light until the visitor picks dark; `SITE.theme.color` gives the theme-color metas.
- coss ui: `src/core/ui/` (shadcn CLI, `components.json`, registry `@coss`). Only components in use are kept: every class in `src/` ends up in the CSS inlined in every page. Add with `npx shadcn@latest add @coss/<name>`.

## Performance rules (PSI mobile 99+)
- Workers Free, for good (Rui, 2026-11-27). These limits are hard rules, shared by every site and job on the account, so one site's mistake takes down the others (on 2026-11-26 one data import used up the day's D1 reads and every D1 site failed until 00:00 UTC):
  - 10 ms CPU per request, 100k Worker requests per day.
  - D1: 5M rows read and 100k rows written per day.
- Public pages, sitemaps, feeds and llms.txt are prerendered static assets: Cloudflare serves them from its cache without running the Worker. Never move a public page or a sitemap to SSR or an API route.
- D1 on a request path: no full-table scans. Every `WHERE`, `JOIN` and `ORDER BY` column has an index (`src/core/db/schema.ts`). Always `LIMIT`, and paginate with a cursor, not `OFFSET`. Check a new query with `EXPLAIN QUERY PLAN`: it must say `SEARCH ... USING INDEX`, never `SCAN`.
- Bulk jobs (imports, backfills, migrations of data, cron sweeps): estimate rows read and written first (rows × passes) and write the estimate in the commit or PR. Process only changed rows, in small batches with pauses. Stop at the first error. Never loop over a whole table per item.
- Write only when data actually changes. Cron, queue and retry paths guard every `UPDATE` with the old value in its `WHERE` (e.g. `status = 'held'`), so a repeat or redelivery writes 0 rows. Never rewrite a row with the values it already has. Inserts that may repeat use `onConflictDoNothing`. The ledger (`src/core/credits/ledger.ts`), cron, queue and webhook follow this.
- Imports into D1: one pass with foreign keys and triggers off (`PRAGMA defer_foreign_keys = ON` and drop/recreate triggers around the load, or load into tables before they get triggers). Measure rows read and written on a small table first (`meta.rows_read` / `rows_written` from `cf d1 query`), multiply by the real row count, and compare with the daily limits before running the full import.
- R2 bills storage and operations above its free tier even on Workers Free. Every upload goes through `putObject` (`src/core/storage/r2.ts`), which refuses objects over `MAX_OBJECT_BYTES` (10 MB). Every prefix that grows has a bound: a rate limit on what creates objects (jobs: 20 per user per minute), and deletion of what expires (the cron deletes mock emails after a day). No per-request `list` on a large prefix.
- Password hashing: PBKDF2-SHA256 at 20,000 iterations (`src/core/auth/hash.ts`, ~2-4 ms). Better Auth's default scrypt (~60 ms) and PBKDF2 at 100k (~11 ms) exceed the CPU limit. A site hasher (`src/site/auth.ts`) must stay in the same range.
- Keep other per-request work small: no heavy SSR, no large JSON parsing or image work in a Worker.
- Every public page is prerendered; all CSS is inlined in `<head>` (`?inline` import in `__root.tsx`); fonts from `SITE.fonts` (`src/core/head.ts`): body `inter` (self-hosted Inter Latin, preloaded) or `system` (nothing loaded), plus an optional `display` heading font (h1-h3, prose headings, `font-heading`), preloaded; every self-hosted font has a metric-matched local fallback, so the swap causes no layout shift. Site colours, radius and surfaces: override the coss tokens in `src/site/styles.css`.
- `src/core/Scripts.tsx` replaces TanStack's `<HeadContent>`/`<Scripts>`: the app JS (entry + modulepreloads) is only added once every element with an `elementtiming` attribute in the first viewport has painted (3 s fallback). Mark the LCP element with `elementtiming="lcp"` (images also `fetchPriority="high"`). Otherwise Lighthouse counts the JS toward LCP and mobile scores drop to 90–95 (seen on Motionboard).
- Popup components (menu, select, dialog, sheet, toast, tooltip, popover) never render in the first screen of a content page and are never imported by the shell; FAQs are native `<details>`; widgets load after hydration inside a fixed-height slot.
- Measured 2026-11-26 on template.krisyang.dev, PSI mobile: home 100/100/100/100, tool page 100/100/100/100.

## Freshness, sitemaps, feed
- `npm run stamp` after editing content. Each tool JSON, guide, legal, about, hub and collection item file has a hash in `content/.hashes.json` (the content without `updated`). Changed files get `updated` set to today, so `lastmod` stays true. `npm test` fails while a hash differs, naming the file. A typo fix: `npm run stamp -- --minor <slug>` (the slug names every language of the page, or `<collection>/<slug>`). New files are recorded as they are. Pages from `extraPages` are not stamped; they set their own `lastmod`. A new page type adds its content folder to `STAMP_DIRS` in `src/core/seo/stamp.ts`. The changelog's `updated` must not be before its newest entry; its `lastmod` is `updated`.
- `sitemap.xml` is an index. Children: `sitemap-tools.xml` (tools), `sitemap-guides.xml` (guides), `sitemap-hubs.xml` (all hubs, page 1 only), `sitemap-<collection>.xml` (items of a collection), `sitemap-items.xml` (item pages without a collection), `sitemap-pages.xml` (home, about, legal, compare, alternatives, glossary, use case, gallery, changelog), `sitemap-video.xml`. Search Console shows the indexed share per file. A child over 45,000 URLs continues in `sitemap-<name>-2.xml`; an empty child is not written. Every URL has `lastmod` and the hreflang alternates of its head, no priority or changefreq. A hub's `lastmod` is its newest member's `updated`. Code: `src/core/seo/sitemaps.ts`.
- `/feed.xml` is RSS 2.0: guides, compare and alternatives pages and the changelog entries in the default language, newest first (`pubDate` = `updated`, or the entry's date; an entry links to its `#<date>-<slug>` anchor), at most 50 items, linked from every page's head. `/changelog/rss.xml` holds the changelog entries only and is linked from the changelog page. `src/core/seo/feed.ts`, written by `scripts/generate.mjs`.
- Deploy: after `cf deploy`, `scripts/check-crawlers.mjs` fetches `/` as Googlebot, Bingbot, OAI-SearchBot, PerplexityBot, Claude-SearchBot and Applebot and expects 200; a block fails the deploy and names the agent (turn off Cloudflare "Block AI bots"). `SITE.seo.allowTraining: false` makes robots.txt disallow GPTBot, ClaudeBot and Google-Extended.
- IndexNow pings only URLs whose `lastmod` changed since the last successful ping (`.indexnow-sent.json`, gitignored; without it, the first run pings everything).

## Accounts, credits, payments (layer 1)
Everything runs in the same Worker as the pages: `src/server.ts` is the entry (`fetch` → TanStack Start, `queue` → job consumer, `scheduled` → cron every 10 min). Turn accounts off with `SITE.accounts.enabled = false` (the header link and account APIs go away).

- Env: `src/core/server/env.ts` (`AppEnv`, `appEnv()`, `flag()`); bindings in `cloudflare.config.ts`. Local values in `.dev.vars` (copy `.dev.vars.example`). Only bindings declared `bindings.secret()` take local values from `.dev.vars` (text bindings cannot be overridden locally), which is why `BETTER_AUTH_URL` is a secret. Production secrets: `cf workers secrets update <NAME> --worker <worker> --type secret_text --text …` for `BETTER_AUTH_URL` (`https://<domain>`), `BETTER_AUTH_SECRET`, `ADMIN_BOOTSTRAP_TOKEN`, and when used `DODO_PAYMENTS_API_KEY`, `DODO_PAYMENTS_WEBHOOK_SECRET`, `RESEND_API_KEY`, `TURNSTILE_SECRET_KEY`, `POSTHOG_KEY`, `GOOGLE_CLIENT_ID/SECRET`. The template demo's values live in the macOS keychain (`site-template-*`). Never print or commit them.
- Mocks (`MOCK_PAYMENTS`, `MOCK_EMAIL`, `MOCK_GENERATION` = `true`): a mock Dodo checkout page (`/api/mock/dodo/checkout`) whose Pay button signs a Dodo-format webhook with the webhook secret and hands it to the real webhook handler; emails stored in R2 under `mock-emails/` and readable at `GET /api/mock/emails` with the `x-bootstrap-token` header; generation by `src/core/jobs/mock-provider.ts` (a prompt containing "fail" fails). The template demo runs fully on mocks.
- DB: `src/core/db/schema.ts` (Drizzle, D1). Better Auth tables + `credit_accounts`, `credit_transactions` (append-only, unique `(type, source_type, source_id)` so nothing applies twice), `credit_reservations`, `payment_orders`, `payment_webhook_events`, `jobs`, `rate_limits`, `admin_users`, `admin_sessions`, `admin_audit_logs`.
- Auth: `src/core/auth/server.ts` (Better Auth: email + password with required verification, Google when its keys are set, Dodo plugin, signup credits in the user-create hook), `session.ts` (`getSessionUser`, `requireUser`), `client.ts`. Pages: `src/routes/{-$locale}/{login,signup,forgot-password,reset-password,account,app}.tsx` (noindex, rendered per request, never prerendered: `PRIVATE_PATHS` in `src/core/pages.ts`).
- Credits: only `src/core/credits/ledger.ts` changes balances (`grant`, `hold`, `commit`, `refund`, `adjust`; each one D1 batch guarded so a failed check changes nothing). Tests: `ledger.test.ts` on in-memory SQLite.
- Payments: `src/core/billing/` (`checkout.ts` creates an order then a Dodo checkout session; `webhooks.ts` verifies amount/currency/product, records the event once, grants credits once, marks the order paid; refunds and failures update the order). Packs: `src/site/plans.ts`. Portal: `POST /api/billing/portal`.
- Jobs: `POST /api/jobs` → `src/core/jobs/create.ts` (Turnstile, rate limit, hold credits, queue message) → `queue.ts` (runs the provider from `src/site/generation.ts`, stores the file in R2, commits; retries 3×, then fails and refunds) → `cron.ts` settles stale reservations. Files: `GET /api/files/<key>` (owner only).
- Abuse: `src/core/security/rate-limit.ts` (D1 fixed window, one atomic upsert), `turnstile.ts` (skipped when no secret key is set).
- Email: `src/core/email/send.ts` (Resend HTTP API), `templates.ts` (verify, reset, receipt; per locale).
- Server analytics and errors: `src/core/server/track.ts` (`trackServer`, `captureServerException` → PostHog `$exception`). Server events carry `$lib: posthog-server`, and inside a request also its user agent and `request.cf.country`.
- Admin: separate identity (not Better Auth). `src/core/admin/` + `src/routes/api/admin/*` + `src/routes/admin/*` (English, no site chrome). First admin: `curl -X POST https://<domain>/api/admin/bootstrap -H "x-bootstrap-token: …" -H 'content-type: application/json' -d '{"email":"…","password":"…"}'` (also resets that admin's password and sessions). Every credit adjust and login is in the audit log.

### Where layer 1 came from

## Adding a page
Pick the type from the table, record where the demand for the keyword was checked, create the files, then `npm run stamp`, `npm test`, `npm run seo-report`. The slug is ASCII kebab-case and the same in every language; a language with no text block or file has no page. Paths below are default-language paths.

| Type | Files to create | URL | Fields beyond the common ones | Minimums (below: noindex) |
|---|---|---|---|---|
| Tool | `content/tools/<slug>.json`, widget in `src/site/tools/index.ts` | `/tools/<slug>/` | `tool`, `steps`, `examples`, `limits`, `sections`, `faq`, `related` | 250 words, 3 to 4 steps, 4 FAQ, 1 example |
| Guide | `content/guides/<lang>/<slug>.mdx` | `/guides/<slug>/` | `kind`, `sources`, `related` | 600 words, 2 H2, 3 internal links, 1 first-hand element |
| Hub | `content/hubs/<id>.json` (`tools`, `guides`, `compare`, `glossary`, a collection) | `/<id>/` | `intro`, `sections`, `faq`, `pageSize` | 6 indexable members (glossary 8), intro 50 words |
| Item | `content/collections/<id>/<slug>.json` ("Add a collection") | `/<id>/<slug>/` | `category`, `media`, `data`, `body`, `alt` | 80 words, media or 10 data entries, 3 related |
| Compare | `content/compare/<lang>/<a>-vs-<b>.mdx` | `/compare/<a>-vs-<b>/` | `products` (2, each `ours` or `third-party`), `verdict`, `table` (`factor`, `a`, `b`, `chooseIf`), `pricing` (`asOf`, `a`, `b`), `sources` | 700 words, 6 table rows, 3 sources |
| Alternatives | `content/alternatives/<product>.json` | `/alternatives/<product>/` | `product`, `criteria`, `entries` (`name`, `url`, `bestFor`, `price`, `relation`, `notes`), `sections`, `sources`, `faq` | 5 entries of 40 words each, 600 words, 3 sources |
| Glossary | `content/glossary/<lang>/<slug>.mdx` | `/glossary/<slug>/` | `definition`, `example` (`text`, `caption`), `seeAlso`, `useIt` (`name`, `path`) | definition 40 to 60 words, definition and body 200 words, 3 see-also, 1 try-it link |
| Use case | `content/use-cases/<slug>.json` | `/for/<slug>/` | `audience`, `problems` (3), `workflow` (3 to 6), `examples`, `cta`, `faq` (3 to 6) | 400 words, 3 examples of 20 words each, near-duplicate at 0.4 |
| Gallery | `content/gallery/<slug>.json`, images in `public/` | `/gallery/<slug>/` | `intro`, `entries` (`media`, `alt`, `title`, `caption`, `facts`, `link`), `faq` | intro 80 words, 6 entries with 15-word captions |
| Changelog | `content/changelog/changelog.json` | `/changelog/` | `entries` (`date`, `slug`, `title`, `items`), newest first | 1 entry |

CJK minimums are 1.8 times the word counts (compare 1260, alternatives 1080, glossary 360, use case 720, gallery intro 144). A text block in JSON has `keyword`, `demand`, `title`, `description`, optional `h1`, `lede`; the file has `slug`, `published`, `updated` (use `YYYY-MM-DD` of today, UTC). In MDX the same fields are frontmatter lines.

Rules for the copy: write for a term someone searches, and check page 1 shows pages of the same type (record it in `demand.note`; `none` is only for hubs, about, legal and the changelog). The title is at most 60 characters (30 CJK) and contains the keyword; the description is 120 to 160 characters (50 to 90 CJK) and answers the query in the first clause; the lede answers in one or two sentences. The h1 contains the keyword. H2s name the reader's questions. Every fact about another product has a source with the date checked, and a price appears only when a source states it; write "not checked" otherwise. Pages with one of our products next to third-party ones show the disclosure line by themselves (`relation: 'ours'`). Alt text describes the image (at most 125 characters). A year in a title only on guides and comparisons, and it must be the year of `updated`. The FAQ is visible text; there is no FAQPage markup.

What fails the build (`npm run build`, `npm run seo-report`): invalid JSON or frontmatter; any schema error (missing field, bad date or slug, title width over 60, description length, keyword not in the title or h1, `demand: none` outside hub/about/legal/changelog, a file name that differs from its `slug`, a compare slug that is not `<a>-vs-<b>`, `updated` before `published`, a changelog out of order or with a repeated `<date>-<slug>` or an `updated` before its newest entry); a keyword, title or description used twice in a language; a collection with more noindex items than `seo.maxNoindexShare`. `npm test` also fails while `content/.hashes.json` differs from the content (run `npm run stamp`) and on any post-build check.

What becomes noindex (the page is built and linkable, with `noindex,follow`, no canonical or hreflang, and left out of the sitemap, llms.txt, hub lists and feeds): content below the minimums above, a near-duplicate of an older page of the same type and language (the later one fails), a hub with too few indexable members, a legal page with `noindex: true`. `npm run seo-report` lists each with its reasons.

JSON-LD (always plus BreadcrumbList, from the visible breadcrumb): compare and alternatives `Article`, glossary `DefinedTerm`, use case, gallery and changelog the breadcrumb only. "Updated <date>" is visible on guides, compare, alternatives, glossary, use case and the changelog, and is the same date as `dateModified`. Sitemap child for all six: `sitemap-pages.xml`. Hubs: add `content/hubs/compare.json` once there are 6 comparisons and `content/hubs/glossary.json` at 8 terms (without the file the page has no hub and the Compare/Glossary breadcrumb level is left out); other types have no hub. Inbound links come from the copy of other pages and from `src/site/nav.ts`; the demo content links to its pages from the case-converter guide.

After editing content: `npm run stamp` (`-- --minor <slug>` for a typo fix), then `npm test` (unit tests, build, output checks) and `npm run seo-report` (noindex reasons, stale pages). Replace the demo pages with the site's own; the template's tests for them run only while the demo files exist.

## Add a collection
A collection is a set of programmatic pages, one per item (symbols, recipes, prompts), each with its own data. The demo is `symbols`.
1. `src/site/collections.ts`: add `defineCollection({ id, categories, data, dataEntries?, dataText? })`. `id` is the folder name and the URL segment (`/<id>/<slug>/`); `categories` are the category ids; `data` is a zod schema for the `data` of an item; `dataEntries(data)` returns the entries of its data block (10 or more count as main content when there is no media); `dataText(data)` returns item-specific text inside `data`.
2. Routes: copy `src/routes/{-$locale}/symbols/` (four files) and rename `symbols` to the id.
3. Hubs: `content/hubs/<id>.json` and `content/hubs/<id>/<category>.json` for every category. A slug cannot be a category id.
4. Items: `content/collections/<id>/<slug>.json` (fields in "Page types", example in `content/collections/symbols/`). Media files go in `public/`. Show the data in the `itemData` slot in `src/site/slots.tsx`.
5. `npm run seo-report` lists every noindex item with its reasons; `npm test`.

An item is noindex (kept out of the sitemap, llms.txt, hub lists and hreflang, still built and linkable) when it has fewer than 80 words / 150 CJK characters of its own text, has no media and fewer than 10 data entries, has fewer than 3 related items, or is a near-duplicate of an older item. The build fails when more than `seo.maxNoindexShare` of a collection's items are noindex: fix the items, do not raise the limit. A schema error, a duplicate keyword, title or description also fails the build. A language the item has no text for has no page.
